# 浏览器 GPU 本地推理

此实现将新的本地神经推理路径约束为 WebGPU。GPU 不可用、初始化失败、算子不兼容或设备丢失时明确报告错误，不自动创建 CPU 推理会话。ONNX Runtime 的 WASM 调度模块、图片预处理和文本后处理仍可使用 CPU；这不等于把神经网络推理改在 CPU 上运行。

## Paddle OCR 与局部修补

- 沿用固定版本、尺寸与 SHA-256 校验的 PP-OCRv6 small 检测器/识别器和 LaMa 数据，不下载可执行代码
- WebGPU 能力检查先于按需下载，避免在不支持的设备上下载后才失败
- `executionProviders: ['webgpu']` 配合 `session.disable_cpu_ep_fallback=1`，默认禁止 ORT 隐式接管不支持的节点。固定 PP-OCRv6 small 识别图使用单独的形状控制配置：实测 277 个节点由 WebGPU 执行，三个整数形状节点由主机处理。此配置开启该图的正常 ORT 分区，并不是逐节点强制白名单；结论仅来自固定模型、锁定运行时和已记录的分区验证，其他适配器仍需复测。不登记 WASM 模型后端，也不在失败后重新创建 CPU 会话
- `ppu-paddle-ocr@6.6.0` 的默认初始化器即使仅指定 WebGPU 也会尝试 CPU；因此直接创建 ORT 会话，再使用该包公开的检测和识别适配器，不调用自动回退工厂
- 检测/识别模型按顺序初始化，降低并行初始化峰值；之后立即解除原始模型字节引用
- 部分初始化失败、取消、设备丢失和释放异常均清理全部已创建会话。第三方按框识别吞掉的 GPU 错误必须重新抛出，不能报告成“没有文字”
- 普通图片既有 Tesseract 路径是独立功能；不将它标记成 GPU OCR，也不以它作为此 GPU 路径的自动回退

## 验证边界

单元测试的模拟对象验证控制流程，不能证明真实模型算子兼容或识别质量。没有可用硬件时可以显式使用软件 WebGPU 验证真实计算，但报告必须注明软件适配器，不能把它当作硬件速度测量。Node Dawn/SwiftShader 验证与扩展浏览器验证也必须分别记录。


LaMa 固定图也需要主机形状控制：实测 4280 个节点分配给 WebGPU，1332 个节点为维度相关运算。原始图递归追溯及仅用于诊断的 Shape 替换试验把这些 CPU 节点限定到了尺寸路径。64×64 图像与蒙版的真实运行产生 3785 次 WebGPU dispatch、有限的 1×3×64×64 输出。此试验只证明算子路径可运行，不证明修补质量或硬件性能。

## 删除实验

在独立源码副本运行了三个删除实验，均使用相同单元测试：

- 删除 GPU 错误捕获：8 项中 1 项失败，设备丢失被 SDK 吞掉后变成成功的空文字；保留
- 删除异步 Worker 启动期间消息队列：首条请求及排队的启动错误响应丢失；保留
- 把完整清理改回顺序释放：8 项中 2 项失败，首个释放错误遮盖初始化错误且跳过第二个会话；保留
- 删除已无生产引用的 `mangaSessionFallback` 及其专属测试，保留无 CPU 重建的路径

WXT 在 Node 中导入入口以提取元数据（[官方说明](https://wxt.dev/guide/essentials/config/entrypoint-loaders)）；延迟加载同时解决锁定依赖内两个 native ORT 版本在 Linux 构建进程冲突的问题。消息队列保证延迟导入不会漏掉首条请求。
